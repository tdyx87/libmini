# libmini RPC 并发模型选型：同步 / 异步 / 流水线

> 数据来源：`example --only rpc` 实测（Windows x86、MinGW Release、本机回环、Tcp 传输、
> handler 固定耗时 5ms），下文每组数据为**两轮独立运行**（R1/R2），复现命令见文末。
> 换机器/构建配置时绝对值会变，**结论的相对关系是稳定的设计事实**。
>
> 本文档只谈**并发模型**——"同一时刻由谁、在哪等结果"。传输层选型
>（HTTP / Tcp / LocalPipe）见 [rpc_transport_guide.md](rpc_transport_guide.md)，
> 两份文档正交：先按部署形态选传输，再按线程/吞吐需求选并发模型。

## TL;DR

- **默认选同步 `call()` + 连接池**：直观、错误处理直白、P50 即单请求真实耗时。
  吞吐天花板 = 并发线程数 ÷ 单请求耗时。
- **业务线程贵/任务量大选 `call_async`**（回调或 future）：吞吐与同步**同档**，
  业务线程占用 **8:1**——异步不创造并发，只是把「等」从业务线程挪进库内执行器。
- **业务线程数 > 8 且 handler 有耗时选流水线**：并发上限从「连接数」解耦为
  「在途上限」，实测 **3.6~3.9x**。
- 三种提交形态的提交开销都在微秒级（future 最差样本 49µs，相对 5ms handler
  仍是 1% 量级）——**选型看收口模型，不看提交开销**。

## 1. 三种模型一览

| | 同步 `call()` | 异步 `call_async`（回调） | 异步 `call_async`（future） | 流水线 |
|---|---|---|---|---|
| 业务线程 | 每请求阻塞一个线程 | 提交后立即返回 | 提交后立即返回 | 不变（同步/异步皆可叠加） |
| 等待发生在 | 业务线程 | 库内执行器（默认 8 线程） | 库内执行器（默认 8 线程） | 业务线程或执行器 |
| 并发来源 | 业务线程数（每线程占 1 条池连接） | **不变**（执行器 N 线程 = N 并发，默认 N=8） | **不变**（同左） | 在途上限（单连接，默认需显式开启） |
| 结果获取 | 返回值 | 回调（错误码/文本为本次专属副本） | `future::get()` 逐个收口 | — |
| P50 含义 | **单请求真实耗时** | 含执行器排队+槽位等待（等待不可见） | 同左 | 单请求真实耗时 |
| 析构安全 | — | 析构排空在途调用，回调不悬空 | 同左 | — |

核心推论（实测反复验证）：**并发上限永远 = 同时处于 `call_core` 里的线程数**
——同步时是业务线程，异步时是执行器线程（默认 8，`set_async_workers` 可调）。`call_async` 改变的是
"谁在等"，不是"有几个在等"；流水线改变的才是"能同时等几个"。

## 2. 实测：同步 vs 异步（Tcp，handler 5ms，各 1600 请求）

| 形态 | QPS (R1/R2) | P50 (R1/R2) | P99 (R1/R2) | 业务线程 |
|---|---|---|---|---|
| 同步 8 线程 | 512 / 504 | 15ms / 15ms | 30ms / 30ms | 8 |
| 异步回调 | 509 / 510 | 1570ms / 1577ms | 3111ms / 3108ms | **1** |
| 异步 future | 494 / 506 | 1568ms / 1586ms | 3125ms / 3129ms | **1** |

- **吞吐比 0.96~1.01x，两轮一致**：同档不是巧合，是结构性的——两种形态的
  服务端侧并发都由 8 个执行者（业务线程或执行器线程）决定。
- **异步 P50（1.57s）不是"请求变慢了"**：它测的是提交→完成的全窗，请求在
  执行器里排队的时间全算在内。同步 P50（15ms）才是单请求真实耗时。
  **做 SLA 监控时不要拿异步库内延迟当端到端口径。**
- 业务线程占用 8:1 是异步的真实收益：8 个原本阻塞在 `call()` 上的线程
  被释放去干别的事（或干脆省掉）。

### 提交开销（µs/次，两轮）

| 形态 | R1 | R2 | 说明 |
|---|---|---|---|
| 回调 | 0.6 | 0.0 | lambda + 队列投递，可内联到接近计时精度 |
| future | 49.4 | 0.0 | 多一次 promise 堆分配 + 共享状态引用计数，波动大 |

- future 最差样本 49.4µs 相对 5ms handler 仍是 **1% 量级**；只有提交频率到
  十万级/秒才需要开始计较。
- **完成等待窗**两形态等价（3138~3159ms，future 略高是逐 future 轮询收口的
  O(n) 扫描）——收口方式不同，总时长相同。

### 回调 vs future 怎么选

- 需要结果对象 / 集中收口 / 提交与消费解耦 → **future**（可传阅、可超时等待）。
- 轻量通知 / fire-and-forget / 流式处理 → **回调**（零收口代码）。
- 两者吞吐与开销同档，**语义差异优先于性能差异**；拿不准选回调（少一层
  future 生命周期管理）。

## 3. 实测：流水线（Tcp，handler 5ms，32 线程共享 1 客户端 × 100 次）

| 配置 | QPS (R1/R2) | P50 | P99 | 提升 |
|---|---|---|---|---|
| 流水线关（池 8 连接 = 8 并发） | 503 / 497 | 60ms | 196/240ms | — |
| 流水线开（单连接，在途上限 64） | 1795 / 1923 | 15ms | 32/30ms | **3.6~3.9x** |

- 32 线程远超池的 8 连接上限：池模式下 24+ 线程在池忙排队，P50 60ms 里
  大半是排队等待（≈4 倍单请求耗时）；流水线把并发上限从「连接数」解耦为
  「在途上限」，排队大幅缓解，P50 降至 15ms（仍含共享单连接的残余排队）。
- **同并发对比不增反降**（8 线程 vs 池 8 连接时两者持平甚至流水线略慢）——
  回环 + 快 handler 下多连接的并行收发占优。流水线的价值只在
  「线程数 > 连接数」的解耦处显现。
- 每连接需严格顺序的会话状态机**不要开流水线**：串行路径响应顺序与请求
  一致，流水线按 id 匹配、顺序无关。

## 4. 模型组合

`call_async` 与同步 `call()` 共用同一请求路径（`call_core`），连接池、流水线、
重试、退避、单次超时对异步自动生效。组合语义：

| 组合 | 并发上限 | 适用 |
|---|---|---|
| 同步 + 池（默认） | 业务线程数（≤池连接数时无排队） | 绝大多数场景 |
| 同步多线程 + 流水线 | min(业务线程数, 在途上限) | 线程多、handler 有耗时 |
| call_async + 池 | **8**（执行器线程数） | 线程贵、吞吐需求 ≤ 8 并发 |
| call_async + 流水线 | **仍 8**（每执行器线程同时 1 个在途请求） | 想要异步收口 + >8 并发时**不够**，见下 |

最后一个组合是常见误区：异步执行器是固定线程池（默认 8），开流水线不会让
并发超过线程数（每个执行器线程同时只有一个在途请求）。**要更大并发只有三条路**：
`set_async_workers` 加大执行器、开更多业务线程跑同步 `call()`（配合流水线解耦
池排队），或降单请求耗时。

## 5. 决策树

```
目标 QPS × 单请求耗时 ≈ 所需并发 C
（例：1000 QPS × 5ms = 5 并发）

C ≤ 8？
├─ 是 → 同步 + 默认池。
│        线程开销嫌大 → call_async（回调/future 按收口模型选）。
└─ 否 → 业务线程能开到 C 个？
         ├─ 能 → 同步多线程 + 流水线（set_pipeline_max_in_flight ≥ C）
         └─ 不能 → call_async 也到不了 C（执行器默认 8 线程）——
                   set_async_workers 加大执行器 / 降单请求耗时 /
                   分片到多客户端实例
```

三条铁律：

1. **异步不创造并发**，只转移等待位置（实测吞吐 0.97~1.01x）。
2. **流水线只在"线程数 > 连接数"时才有收益**，同并发下反而可能略慢。
3. **异步 P50 含排队等待**，SLA 口径必须用端到端业务计时。
