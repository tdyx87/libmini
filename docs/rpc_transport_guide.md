# libmini RPC 传输选型与并发模型

> 数据来源：`example --only rpc` 实测（Windows x86、本机回环），复现命令见文末。
> 换机器/构建配置时绝对值会变，**结论的相对关系是稳定的设计事实**。

## TL;DR

- **本机进程间（IPC）**：选 **LocalPipe**（Windows 命名管道 / POSIX UDS）——吞吐最高、
  不占端口、受系统 ACL 保护。
- **跨机内网**：选 **Tcp** 帧协议——比 HTTP 少协议头开销，语义与其他传输完全一致。
- **对外兼容生态**：才考虑 **HTTP**——curl/浏览器/网关友好，但本机性能明显落后。
- **高频调用**：连接池默认开（与每调用重连差 9x）；handler 有耗时且线程数多时
  再开**流水线**（并发上限从「连接数」解耦为「在途上限」，实测 3.9x）。

## 1. 三传输对比（本机实测）

| 传输 | QPS | P50 | P99 | 说明 |
|------|-----|-----|-----|------|
| LocalPipe | 11 940 ★ | ~0ms | ~0ms | 命名管道（Windows）/ UDS（POSIX） |
| Tcp | 9 756 | ~0ms | 1ms | 裸 TCP 帧协议（u32 长度 + 1 类型 + JSON） |
| HTTP | 1 626 | 1ms | 25ms | cpp-httplib，HTTP/1.1 全套语义 |

- 管道 ≈ 1.2x Tcp（同档，都在万级）；两者都是 HTTP 的 6~7x。
- HTTP 的差距来自：头解析/状态码/分块编码 + 实测尾部抖动（P99 25ms）。
- **语义零差异**：重试/退避/429/过载排队/统计/优雅停机在三传输完全一致，
  切换只改构造函数——先按部署形态选，性能不是第一决定因素。
- 测量口径：8 线程 × 200 次，每线程独立客户端，handler 无耗时，本机回环。

### 各传输的运维特征

| 维度 | LocalPipe | Tcp | HTTP |
|------|-----------|-----|------|
| 端口占用 | 无（命名空间内唯一） | 需要 | 需要 |
| 访问控制 | 系统 ACL / 文件权限 | 自行实现 | 自行实现 |
| 跨机 | 否（`\\.\pipe\...` / UDS） | 是 | 是 |
| 工具生态 | 平台专用 | tcpdump | curl/网关/浏览器 |
| 连接复用 | 池/流水线可用 | 池/流水线可用 | httplib keep-alive |

## 2. 并发模型：连接池 vs 流水线

### 两种上限，两种瓶颈

| | 连接池（默认） | 流水线（`set_pipeline_max_in_flight(n)`） |
|---|---|---|
| 并发上限 | 连接数（`set_connection_pool_max`，默认 8） | 在途上限 n（单连接） |
| 每请求开销 | 取还连接（锁 + 队列） | 请求注入自增 id + 在途表匹配 |
| 服务器侧 | 每连接独立处理 | 同连接多请求并发（响应按 id 回带，乱序无害） |
| 失败语义 | 池忙排队超时 → TIMEOUT | 槽位等待超时 → TIMEOUT；断线自动重建 |

### 实测（Tcp，handler 5ms，32 线程共享 1 客户端 × 100 次）

```
流水线关（池 8 连接 = 8 并发）: QPS=516   P50=60ms  P99=198ms
流水线开（单连接 64 在途）    : QPS=2029  P50=15ms  P99=27ms   → 3.9x
```

- **同并发对比不增反降**：8 线程 vs 池 8 连接时两者持平甚至流水线略慢
  （0.47x）——回环 + 快 handler 下多连接的并行收发占优。流水线的价值
  只在「线程数 > 连接数」的解耦处显现。
- **池关 vs 池开**（300 次顺序调用）：227 → 2083 QPS（9.2x）。
  池是默认开的，此数据主要用于评估「禁用池」的代价。

### 选型细则

- **请求稀疏 / 低频**：默认即可（池 + 串行）。
- **线程多、handler 有耗时**（推解析、批处理 fan-out）：开流水线，
  在途上限设为「可接受的服务端压力」而非线程数。
- **每连接需严格顺序**（如同会话状态机）：不开流水线（串行路径响应
  顺序与请求一致；流水线按 id 匹配，顺序无关）。
- **客户端线程数巨大**：线程数 ≥ 连接上限时，池忙排队会先于业务超时
  爆发——用流水线把并发与连接数解耦。

## 3. 决策树

```
需要跨机？
├─ 是 → 需要兼容 HTTP 生态（网关/curl/浏览器）？
│        ├─ 是 → HTTP（接受性能差距）
│        └─ 否 → Tcp 帧协议
└─ 否（本机 IPC）→ LocalPipe（管道/UDS）
      （不占端口 + ACL；性能与 Tcp 同档甚至更高）

同一客户端调用并发模型：
├─ QPS < 千级 / 请求稀疏
│        └─ 默认：连接池（8 连接）
├─ 线程数明显多于 8 且 handler 有耗时
│        └─ set_pipeline_max_in_flight(16~64)
└─ 需要同连接严格顺序
         └─ 池 + 串行（不开流水线）
```

## 4. 与过载控制/优雅停机的配合

- **过载闸门是服务端并发的真上限**：无论客户端并发模型多激进，
  服务端 `max_in_flight`/队列达到上限即 429（带 Retry-After）。
  流水线在途上限只是客户端自我约束。
- **优雅停机**：stop() 后新请求 429 `server shutting down`，排空窗口
  （默认 3s）内已接收请求处理完；排水期不回包——客户端断连重试衔接
  新实例，滚动重启零失败（见 README RPC 节）。
- **容量估算**：客户端总并发 ≈ min(线程数, 池连接数或流水线在途上限)；
  服务端容量 = max_in_flight + 队列深度。前者要贴近后者，避免
  「客户端排队等池/槽位」隐藏真实服务端能力。

## 5. 可观测性（压测时的健康信号）

- **客户端** `pool_stats()`：池 created/reused/closed；流水线
  `pipeline_in_flight(_peak)` / `reused_total` / `broken_total` /
  `slot_wait_total` / `slot_timeout_total`——slot 等待/超时占比高 =
  上限偏小；broken 高 = 连接质量/服务器重启频繁。
- **服务端** `stats()`：completed/rejected 合计与 **Http/Tcp/Local 分列**、
  活跃/队列实时值与峰值、请求级格式错误（malformed 列）。
- **延迟分位**：`latency_stats()` 全局 + 按传输过滤（`RpcTransportFilter`），
  客户端/服务端交叉对比定位「慢在链路还是慢在处理」。
